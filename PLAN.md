# Adventure Engine — Project Plan & Design Document

> Living document. Updated throughout the design/development conversation.
> Last updated: 2026-10-29

---

## Vision

A browser-based single-player escape room game where:
- The player is always **the captive** — trapped in a room, solving puzzles to escape
- The antagonist is always an **AI-controlled killer** with configurable personality/behavior
- Every scenario is defined as **JSON + background images** — no code changes needed for new content
- The JSON schema is rich enough to represent the best mechanics from classic point-and-click adventures, horror games, immersive sims, puzzle games, stealth games, and real escape rooms
- Scenarios can be **generated by AI** — give an LLM the schema spec and a theme, get a playable level
- Future: **open marketplace** where players download community/AI-generated scenario manifests
- Future: **multiplayer** — second player takes over the killer role, or co-op escapers

## User Preferences

- **Stack**: Java backend (Spring Boot, Maven) + React/TypeScript frontend (Vite, Phaser 3)
- **Java 21**, Spring Boot 3.3.5
- **No Gradle** — Maven only
- **Shared inventory** (not per-player) for simplicity
- **Backgrounds are human-provided art** — the AI generates everything else
- The entire scenario must be representable as **JSON + background images only**
- Design for multiplayer from the start (don't paint into a corner) but build single-player first

## Architecture

### Current State
- Spring Boot server with raw WebSocket at `/ws/game`
- React + Phaser 3 client with Vite
- Hardcoded captive/killer interaction logic in GameSession.java
- 2-player lobby with room codes, role selection
- Basic HUD: noise bar, suspicion bar, killer warning, inventory bar

### Target Architecture (Single Player)
- **Server**: Spring Boot runs game engine + killer AI. Loads scenarios from JSON.
- **Client**: React + Phaser renders the room, handles verb-based interactions, sends actions via WebSocket
- **Lobby simplifies**: Title screen → Play / Select Scenario → Game starts
- **No room codes** in single player (auto-created session)
- **Killer AI**: Server-side state machine, configurable per scenario via JSON
- **Scenario engine**: Generic interpreter — conditions + effects, no scenario-specific code

### Multiplayer-Ready Design
- Server stays as game authority in both modes
- Player abstraction: human (WebSocket) or AI (server-side driver) — same interface
- Room code system stays in code, just hidden in single-player
- Scenario JSON has optional `mode` field for future multiplayer variants

## The Scenario Schema

### Core Principle
**JSON + background images = complete scenario.** No code changes, no plugins, no scripting language. The schema must be expressive enough to represent the most complex classic adventure game puzzles purely through structured data.

### Interaction Verbs (from the classics)

| Verb | Inspired By | What It Does |
|------|------------|--------------|
| `look` | Sierra eye icon, Monkey Island "Look at" | Examine visually. Get description. Always safe, zero noise by default. THE discovery verb. |
| `hand` | Sierra hand icon, MI "Use/Push/Pull/Open/Close" | Touch, push, pull, open, close, flip, manipulate with bare hands. |
| `take` | Sierra hand icon, MI "Pick up" | Pick up object and add to inventory. |
| `talk` | KQ6 talk icon, MI "Talk to" | Speak, read aloud, listen, whisper, shout. Even solo — inner monologue, read inscriptions, listen at door. |
| `use_item` | KQ5/6 current-item icon, MI "Use X with Y" | Apply an inventory item to a world object. Requires `item` field. THE puzzle verb. |

### Puzzle Types the Schema Must Support

**From King's Quest 5/6:**
- Use item on object (key → lock)
- Multi-step chains (5-6 steps deep)
- Item combinations (merge two items)
- Red herrings / wrong tools
- Dual-purpose items (examine reveals hidden function)

**From Monkey Island / LucasArts:**
- Dialogue as puzzle (talk to learn, convince, distract)
- Distraction mechanics (lure someone away)
- No dead ends — always solvable
- Alternate solutions (multiple paths)
- Transformation chains (modify items step by step)

**From Myst:**
- Environmental manipulation (switches, dials, levers, machinery)
- Code/pattern input (enter combination, match symbols)
- Sequence puzzles (do steps in correct order)
- Observation puzzles (notice a detail, apply knowledge elsewhere)
- Sound-based clues

**From Grim Fandango / Day of the Tentacle:**
- Multi-state machinery
- Story-integrated puzzles (every puzzle serves narrative)
- Environment changes over time

**Unique to Adventure Engine:**
- AI killer antagonist with configurable personality
- Noise meter as risk/reward mechanic (and strategic tool)
- Hiding spots with tension
- Killer evidence system (killer notices changes on visits)
- Environment changes between killer visits
- Phase-based escalation (killer gets more aggressive as you progress)

### Schema Sections

1. **Metadata** — id, title, description, difficulty, tags, estimated time
2. **Setting** — background_key (maps to art asset), fallback room_style, ambient text
3. **Flags** — global key-value pairs for tracking progress
4. **Items** — collectible inventory items with examine interactions
5. **Combinations** — merge two items into a new item
6. **Objects** — world objects with position, visual, states, verb-based interactions
7. **Puzzle Objects** — special interactive elements (combination locks, toggle panels, sequence puzzles, dials)
8. **Phases** — story progression stages with narrative text and killer behavior overrides
9. **Events** — triggered narrative moments (time-based, condition-based)
10. **Killer AI** — personality, behavior parameters, search behavior, dialogue, special behaviors, on-visit effects
11. **Win Conditions** — what triggers escape/victory
12. **Lose Conditions** — what triggers failure (caught, time limit)
13. **Hints** — progressive help system
14. **Solution Paths** — documented paths for validation (quiet path, loud path, etc.)

### Condition System

Conditions gate when interactions fire. AND by default, with `any_of`/`all_of` for composition.

Types: `object_state`, `has_item`, `not_has_item`, `flag_is`, `flag_not`, `noise_above`, `noise_below`, `phase_is`, `time_after`, `item_count`, `is_hiding`, `killer_is`, `any_of`, `all_of`

### Effect System

Effects are what happen when an interaction fires. Execute in order.

Types: `message`, `add_item`, `remove_item`, `set_state`, `show_object`, `hide_object`, `set_flag`, `add_noise`, `set_noise`, `advance_phase`, `game_over`, `start_hiding`, `stop_hiding`, `transform_item`, `trigger_event`, `visual_cue`, `cycle_state`, `add_time`, `play_sound`

### Puzzle Objects (Beyond Standard Verb Interactions)

For Myst-style interactive elements that need their own UI:
- **combination_lock** — N digit dials, player sets each, checks against solution
- **toggle_panel** — N switches with on/off states, correct pattern unlocks
- **sequence_puzzle** — do N steps in correct order
- **dial** — rotate through positions to correct value
- **keypad** — enter a numeric code
- Future: slider_puzzle, wire_connect, pipe_routing

### Item Examination

Items have their own interactions when examined in inventory:
- `look` — closer inspection, may reveal clues (set flags)
- `hand` — manipulate (break open, flip over, unfold)
- Items can carry hidden information revealed only on examination

### Killer AI Configuration

Per-scenario killer personality:
- **Base behavior**: check intervals, noise thresholds, decay rates, warning/search durations
- **Variance**: randomness in timing to prevent gaming the pattern
- **Thoroughness**: probability of finding player in hiding spots (0.0 - 1.0)
- **Evidence awareness**: killer notices state changes (empty chair, open safe) and escalates
- **Personality dialogue**: approach lines, search lines, clear lines, evidence lines, catch lines
- **Special behaviors**: triggered by conditions (phone distraction, enraged mode)
- **On-visit effects**: killer changes environment when checking (relocks things, moves items)
- **Phase overrides**: behavior changes per story phase

### Noise as Strategy (Two-Way Mechanic)

Noise isn't just risk — it's a tool:
- Make noise intentionally to lure killer upstairs (creates window for time-sensitive effects)
- Some interactions REQUIRE noise (smash glass, bang on pipe to signal)
- Noise triggers can cascade (knock over bucket → killer investigates → timer event fires)
- Strategic tradeoff: louder actions are faster/more direct but riskier

### Validation Rules for Valid Scenarios

1. All referenced IDs (items, objects, flags) must exist in their definitions
2. No orphaned items (defined but never obtainable)
3. At least one win path must be completable from initial state
4. No dead ends (item consumed that's required downstream)
5. Puzzle objects have valid solutions
6. At least one hiding spot exists and is reachable
7. All flags used in conditions are initialized or set by an effect somewhere
8. Noise values stay within 0-100 range
9. Phase transitions don't create infinite loops
10. Killer parameters are in valid ranges
11. Every object referenced in effects exists in objects[]
12. Combination results are defined in items[]

### Design Patterns for AI Scenario Generation

30 proven patterns for creating scenarios. Drawn from classic point-and-click adventures AND adapted from horror, immersive sims, puzzle games, stealth games, real escape rooms, and narrative games. All representable in the existing schema with no code changes. A typical scenario uses 8-12 patterns; C(30,10) = **30 million+ unique pattern combinations** before accounting for theme, narrative, and item variations.

**Structure Patterns** (how puzzles connect)
1. **The Gateway Puzzle** — First puzzle has no prerequisites. Builds confidence.
2. **The Dependency Chain** — A → B → C → D. Linear progression backbone.
3. **The Fork** — Two independent chains that converge at a shared goal.
4. **The Progressive Reveal** — Each puzzle solved reveals more room/story.
5. **The False Summit** — Player thinks they can escape, one more obstacle appears.

**Item & Knowledge Patterns** (what the player works with)
6. **The Dual-Purpose Item** — One item solves a puzzle AND carries a clue for another.
7. **The Nested Secret** *(The Room)* — Object within object within object, each layer reveals more.
8. **The Knowledge Gate** *(Myst, Outer Wilds)* — Information, not items, gates progress. The player carries knowledge.
9. **The Revelation Tool** *(real escape rooms)* — An item (UV light, lens) that reveals hidden info on existing objects. Re-examine everything.
10. **The Cross-Reference Deduction** *(Return of the Obra Dinn)* — Multiple clues the PLAYER must synthesize mentally. No flag gates the answer.

**Risk & Reward Patterns** (tension with the killer)
11. **The Noise Tradeoff** — Loud solution vs. quiet solution. Risk vs. reward.
12. **The Evidence Gamble** — Solving a puzzle leaves visible changes. Killer notices on next visit.
13. **The Distraction Window** — Intentional noise lures killer, creating a timed opportunity.
14. **The Ticking Clock Decision** — Two time-sensitive things at once. Player must choose.
15. **The Bait and Punish** *(survival horror)* — Obvious solution works but costs dearly. Patient player finds the better path.
16. **The Sound Masking** *(stealth games)* — Environmental noise covers your actions temporarily.
17. **The Trap Setting** *(stealth games)* — Rig the environment against the killer proactively.

**Solution Design Patterns** (how puzzles are solved)
18. **The Red Herring** — Wrong approach fails with an informative message. Failure teaches.
19. **The Emergent Combination** *(immersive sims)* — Two simple mechanics combine for an "aha!" solution.
20. **The Multi-Path Solution** *(immersive sims)* — Same obstacle, genuinely different approaches with different costs.
21. **The Rule Subversion** *(Baba Is You)* — Change the constraint instead of satisfying it.
22. **The Myst Machine** — Multi-state environmental puzzle with interacting controls.
23. **The Power Routing** *(Myst)* — Limited resource allocation between competing devices.
24. **The Perspective Alignment** *(The Witness)* — Pattern visible only from a specific viewpoint/closeup.

**Story & Choice Patterns** (narrative structure)
25. **The Moral Fork** *(Telltale, Undertale)* — Mutually exclusive choice leading to different endings.
26. **The Accomplice** *(adventure games, escape rooms)* — NPC ally behind a barrier. Talk and trade through gaps.
27. **The Point of No Return** *(survival horror)* — Irreversible action the player must commit to. Rewards preparation.

**Environment & Adaptation Patterns** (the room fights back)
28. **The Camouflage** *(Adventure Engine-unique)* — Hide evidence of progress so the killer doesn't escalate on visits.
29. **The Echo** *(Myst, Day of the Tentacle)* — Action in one view produces observable effect in another. Spatial cause-and-effect.
30. **The Decay Clock** *(Adventure Engine-unique)* — Puzzles get harder over time as the killer adds obstacles on visits. Early action = easier escape.

## Implementation Phases

### Phase 1: Schema & Engine (Server)
- Define JSON schema as Java POJOs (ScenarioDefinition)
- Build ScenarioLoader (reads JSON from resources/scenarios/)
- Build ScenarioEngine (generic condition/effect interpreter)
- Build PuzzleEngine (handles puzzle objects: locks, panels, sequences)
- Build one complete scenario: captive-classic.json
- Replace hardcoded GameSession logic with engine calls

### Phase 2: Killer AI (Server)
- KillerAI state machine (idle → curious → investigating → checking → returning)
- Game tick loop (1 tick/sec via ScheduledExecutorService)
- Wire AI into GameSession
- Noise decay logic
- Evidence detection on visits
- On-visit environment effects

### Phase 3: Client Simplification
- Strip lobby to single-player flow
- Add verb selector UI (look/hand/take/talk + current item)
- RoomScene renders objects from scenario data (not hardcoded configs)
- Puzzle object UIs (combination lock, toggle panel, keypad, etc.)
- Item examination screen
- Killer approach/search/clear message display
- Background image loading from scenario's background_key

### Phase 4: Schema Validation & Tooling
- JSON schema validation on load
- Reachability analysis (can win conditions be met?)
- Dead-end detection
- Second scenario to prove engine is generic
- Error messages for invalid scenarios

### Phase 5: Polish & Marketplace Prep
- Scenario browser/selector
- Difficulty ratings
- Hint system UI
- Sound/music hooks in schema
- Scenario packaging format (JSON + images as zip?)
- Documentation site for scenario creators

## Key Design Decisions (Resolved)

### Background Images & Views
- A scenario has **one main background** (the room) plus optional **closeup views** (desk surface, safe panel, window detail)
- Each view is a separate background image with its own set of visible/interactable objects
- `views[]` section in schema defines additional views, each with a background key and object list
- A `set_view` effect switches between views (+ a back action to return)
- This means a scenario needs 1-N background images depending on complexity
- AI generates scenario with view descriptions → human creates matching art

### Object Rendering: Hotspot Model
- When a background image exists: objects are **invisible hotspot regions** overlaid on the art. The visual IS the painted background. Classic adventure game approach.
- When no background image exists: objects render as **colored rectangles with labels** (current system). This is the prototyping/fallback mode.
- Same JSON either way — `visual` config used only in fallback mode, `position` + `size` define the clickable hotspot region in both modes.

### Puzzle Widgets: Pre-built Component Library
- Complex interactive puzzles (combination locks, keypads, toggle panels, sequence puzzles, dials, wire-connect) are **pre-built client components** parameterized by JSON config
- Adding a NEW widget type requires a code release, but new scenarios using existing widgets don't
- The widget library grows over time; initially: combination_lock, keypad, toggle_panel, sequence_puzzle, dial
- Widgets render as React overlays on top of the Phaser canvas (or as Phaser UI scenes)

### Coordinates: JSON-First Workflow
- AI generates scenario with approximate positions
- Procedural fallback renderer shows layout as a visual guide
- Artist creates background art to match the layout
- Fine-tuning coordinates after art is created is a quick JSON edit
- Future: visual scenario editor tool
